## Parecer B4 (terceira rodada): base `FROM medical-classifier:local`

### O que foi inspecionado e não apresentou defeito estático

- **PATH** (`Dockerfile.airflow:5`): `/opt/airflow-venv/bin` é prefixado ao PATH herdado (`/opt/venv/bin:/usr/local/bin:...`). Assim `airflow`, `python` e `gunicorn` resolvem para o venv do Airflow. O comando do CI `run --rm -T airflow python -` e a sonda do Compose usam esse `python`, que possui `airflow.models`. Coerente.
- **Venvs isolados**: o venv do Airflow é criado a partir de `/usr/local/bin/python`, que existe na imagem oficial. O modelo continua em `/opt/venv`, instalado no estágio runtime do `Dockerfile:38` pelo pip desse venv.
- **Link `/opt/model-venv`** (`Dockerfile.airflow:26`): o interpretador resolve `pyvenv.cfg` pelo caminho não canonizado, então `/opt/model-venv/bin/python` ativa o prefixo `/opt/venv`. A linha 36 valida isso em build. A DAG usa caminho absoluto, imune ao PATH do processo pai.
- **Permissões**: `mkdir` e `chown -R 10001:0` estão na mesma camada, sem duplicação. O volume `airflow-estado` novo herda proprietário 10001:0. Os volumes externos foram criados pela stack principal com UID 10001, então o Airflow (10001:0) escreve neles.
- **Herança**: a imagem base não tem ENTRYPOINT. `HEALTHCHECK NONE` anula a sonda da porta 8000 e o CMD é substituído. `docker compose run ... airflow db migrate` executa `airflow` diretamente, sem entrypoint oficial interferindo.
- **Standalone**: com SQLite o Airflow força `SequentialExecutor`, compatível com o Compose. `bash` existe na imagem slim, logo o BashOperator funciona.
- **CI**: `shell: bash` explícito ativa `pipefail`, então o `tee` da linha 71 não mascara falha. A ordem `build api` antes de `build airflow` garante a base.
- **Constraints**: o commit é imutável e o `--checksum` fixa o conteúdo. Não pude verificar de forma independente que o commit informado corresponde à tag `constraints-2.11.0`.

### Achados

**1. Média. `Dockerfile.airflow:19`. `ADD --checksum` sem diretiva `# syntax=`.**
Reprodução: construir com o builder legado (`DOCKER_BUILDKIT=0`) ou com Docker Engine anterior à 25 e BuildKit menor que 0.12.
Consequência: erro imediato `unknown flag: --checksum` antes de qualquer camada, exatamente no host que está em recuperação. Não afeta o runner do GitHub, que é recente.
Correção mínima: adicionar `# syntax=docker/dockerfile:1.7` como primeira linha. O frontend é baixado uma vez e é pequeno.

**2. Média. `Dockerfile.airflow:2` e `docker-compose.airflow.yml:5`. Base é uma tag mutável local sem verificação de correspondência.**
Reprodução: alterar `src/` ou `requirements.lock`, executar apenas `docker compose -f docker-compose.airflow.yml build`.
Consequência: a imagem do Airflow é construída sobre uma versão antiga do modelo, e o `ln -s` e a validação da linha 36 passam mesmo assim. O CI evita isso pela ordem dos passos, mas o fluxo local não tem guarda. Com o driver `docker-container` do buildx, a tag local nem é visível e o build falha por tentativa de pull.
Correção mínima: `ARG BASE_IMAGE=medical-classifier:local` e `FROM ${BASE_IMAGE}`, mais um script ou alvo que construa a API antes e passe o ID da imagem. Documentar que o driver padrão é obrigatório.

**3. Baixa. `Dockerfile.airflow:14` e `23`. `--no-compile` somado a `PYTHONDONTWRITEBYTECODE=1` no venv do Airflow.**
Reprodução: cronometrar `airflow db migrate` ou observar o tempo até `/health` responder no `standalone`.
Consequência: cada processo do Airflow (scheduler, webserver, triggerer, processador de DAG, cada `airflow` do CI) compila bytecode em memória a cada partida. Isso alonga o `start_period` de 60 s e o passo do CI. O ganho de tamanho é real, mas o custo de latência não foi medido. Não é defeito, é troca não quantificada.
Correção mínima: medir. Se necessário, rodar `python -m compileall -q /opt/airflow-venv/lib` na mesma camada e registrar o tamanho resultante.

**4. Baixa. `Dockerfile.airflow:22`. `pip` do venv do Airflow não é pinado.**
Reprodução: reconstruir após uma nova imagem `python:3.11.16-slim-bookworm` com `ensurepip` atualizado.
Consequência: o resolvedor muda entre builds. Os constraints e o `pip check` mitigam quase todo o risco, mas a reprodutibilidade bit a bit não é garantida.
Correção mínima: `pip install "pip==X.Y"` antes do Airflow, ou aceitar e documentar.

**5. Baixa. `Dockerfile.airflow:31`. Comentário fora de lugar.**
O texto sobre o link refere-se à linha 26, mas está acima do `COPY dags`. Mover o comentário para a linha 25. Sem impacto funcional.

### Dúvidas e falta de evidência, não defeitos

- **Nenhum build desta variante foi feito.** Não há prova de que `pip install apache-airflow==2.11.0` com esses constraints resolve em Python 3.11.16 na imagem slim, nem de que a linha 37 importa `BashOperator` sem erro. A validação `compose config` não cobre isso.
- **A economia de 686 MiB é dedução de camadas compartilhadas**, não medida. Vale também notar que o venv do Airflow adiciona várias centenas de MiB próprios. Recomendo registrar `docker image ls` e `docker system df` após o primeiro build bem-sucedido.
- **DagBag e conclusão da DAG continuam sem evidência real**, como o orquestrador já reconheceu. Os testes locais (API 37, tarefas 16) não exercitam o Airflow.
- **Chaves `FERNET_KEY` e `SECRET_KEY` ausentes** não mudaram nesta rodada. Registro apenas que o `standalone` seguirá com avisos e chave padrão do webserver, aceitável para exposição em `127.0.0.1`.

Análise estática do snapshot. Não verifiquei o SHA-256 nem o commit dos constraints, a existência da tag `python:3.11.16-slim-bookworm`, nem o comportamento em tempo de execução. A ausência de defeitos críticos aqui não substitui um build e uma execução da DAG registrados como evidência.
